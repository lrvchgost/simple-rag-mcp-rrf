# Архитектура: RAG Knowledge Base — MCP-сервер с локальной LLM

Документ описывает архитектурные принципы, структуру компонентов, зоны ответственности и
логику работы системы управления знаниями на базе Model Context Protocol (MCP), LangGraph
и локальной LLM (Ollama).

## 1. Архитектурные принципы

- **SRP (Single Responsibility Principle).** Каждый компонент отвечает ровно за одну
  изолированную задачу: парсинг файлов отделён от логики гибридного поиска, поиск —
  от генерации ответов, оценивание чанков — от оркестрации графа.
- **DIP (Dependency Inversion Principle).** Доменный слой и граф вычислений не зависят
  от конкретных библиотек или внешних сервисов (ChromaDB, Ollama REST API, rank_bm25).
  Все внешние интеграции вынесены за абстрактные интерфейсы (`src/domain/interfaces.py`);
  реализации внедряются снаружи (Dependency Injection). Домен не импортирует ничего
  из инфраструктуры — только свои абстракции.
- **Модульность.** Система разделена на три независимых слоя. Любой компонент
  (например, векторное хранилище) заменяется без изменения логики Core RAG.

### 2.1. Интерфейсный слой — `src/server.py`

Внешняя точка входа для host-агентов (Claude Desktop, VS Code Copilot и др.).

- Регистрация 4 инструментов MCP через декораторы FastMCP.
- **Семантические метаданные.** Каждый инструмент снабжён исчерпывающим полем
  `description` (docstring функции). Host-агент самостоятельно анализирует описания,
  чтобы решить, какой инструмент вызвать под запрос пользователя — без подсказок.
  Это требование ТЗ и проверяется на сдаче.
- Валидация входов, сборка зависимостей (DI), человекочитаемая обработка ошибок:
  вместо traceback инструмент возвращает понятное сообщение и подсказку
  (например, «Ollama недоступна» или «индекс пуст — вызовите index_folder»).
- Транспорт: `stdio` (локально, по умолчанию) или `http` (в Docker Compose),
  управляется переменной `MCP_TRANSPORT`.

### 2.2. Доменный слой — `src/domain/`

| Компонент | Ответственность (SRP) |
|---|---|
| `DocumentIndexer` | Обход директории по glob, выбор сплиттера под формат, вычисление метаданных (`source`, `line_number`, `file_type`), запись чанков в хранилища и перестройка BM25 |
| `HybridRetriever` | Параллельный запуск векторного и лексического поиска и слияние выдач по Reciprocal Rank Fusion (RRF). Используется и внутри графа, и инструментом `find_relevant_docs` напрямую |
| `CorrectiveRAGGraph` | Оркестрация пайплайна на `langgraph.StateGraph`: узлы, условные переходы, ограничение retry-циклов |

Абстракции (`interfaces.py`), от которых зависит домен:

- `VectorStorage` — `add`, `search`, `all_chunks`, `count`, `delete_by_sources`, `clear`;
- `SparseStorage` — `build(chunks)`, `search`, `count`;
- `EmbeddingService` — `embed(texts) -> list[list[float]]`;
- `LLMService` — `generate(prompt, system_prompt, json_mode) -> str`, `check_availability()`.

### 2.3. Инфраструктурный слой — `src/infrastructure/`

| Адаптер | Реализует | Детали |
|---|---|---|
| `ChromaVectorStorage` | `VectorStorage` | In-process ChromaDB (`PersistentClient`). Векторы вычисляются внедрённым `EmbeddingService` и передаются явно — Chroma хранит только векторы, что позволяет переключать провайдера эмбеддингов без изменения адаптера |
| `BM25SparseStorage` | `SparseStorage` | `rank_bm25.BM25Okapi`; токенизация: нижний регистр, разбор camelCase и snake_case (`TOKEN_EXPIRY_HOURS → token, expiry, hours`), поддержка кириллицы |
| `DefaultChromaEmbedding` | `EmbeddingService` | Дефолтная модель ChromaDB (ONNX MiniLM-L6-v2, локально, без API) |
| `OllamaEmbedding` | `EmbeddingService` | Внешняя модель через Ollama REST (`/api/embed`), например `nomic-embed-text` (опциональное задание ТЗ) |
| `OllamaService` | `LLMService` | Обёртка над локальным REST API Ollama (`/api/generate`, `stream=false`), режим `json` для структурированных ответов, retry с backoff, `temperature=0` |

Провайдер эмбеддингов выбирается одной переменной окружения `EMBEDDING_PROVIDER`
(`default` или `ollama`) — остальной код изменений не требует (фабрика в `server.py`).

## 3. Гибридный поиск и RRF

Цель — одинаково высокая точность на смысловых вопросах («как устроена авторизация»)
и точечных запросах по идентификаторам («где используется `TOKEN_EXPIRY_HOURS`»).

1. **Dense (векторный):** запрос → эмбеддинг → ChromaDB → топ-K по расстоянию.
2. **Sparse (лексический):** запрос → токенизатор → BM25 → топ-K по окапированному TF-IDF.
3. **Reciprocal Rank Fusion:** скоры ChromaDB (0–1) и BM25 (0–∞) несопоставимы,
   поэтому слияние выполняется по позициям в выдаче, а не по значениям:

   ```
   RRF(d) = 1 / (k + r_dense(d)) + 1 / (k + r_sparse(d))   при k = 60
   ```

   где `r(d)` — позиция документа в списке (с 1); если документ отсутствует в списке —
   слагаемое не учитывается. Документы с наибольшим суммарным баллом идут дальше.

Оба поиска запускаются параллельно (`ThreadPoolExecutor`), но слияние детерминировано:
при равенстве RRF-баллов выше документ из векторной выдачи.

## 4. Пайплайн Corrective RAG (LangGraph)

```
                       ┌─────────────────────────┐
                       │        START            │
                       └───────────┬─────────────┘
                                   ▼
                       ┌─────────────────────────┐
              ┌──────► │  Node: Retrieve (RRF)   │  1-й проход — исходный
              │        └───────────┬─────────────┘  вопрос пользователя
              │                    ▼
              │        ┌─────────────────────────┐
              │        │  Node: Grade Chunks     │
              │        └───────────┬─────────────┘
              │                    ▼
   [мало релевантных           ┌─────────────────────────┐
    и циклов < 2]              │  Conditional Edge       │
              │                └───────┬─────────┬───────┘
              │                        │         │
              │           1-й ретрай:  │         │ достаточно релевантных
              │           Rewrite;     │         │ или исчерпаны циклы
              │           2-й+:        │         │
              │           Broaden      │         │
              ▼                        ▼         ▼
   ┌───────────────────┐    ┌─────────────────────────┐
   │ Node: Rewrite или │    │  Node: Generate Answer  │
   │ Broaden (loop+1)  │    │  → answer + sources     │
   └─────────┬─────────┘    └───────────┬─────────────┘
             │                          ▼
             └──────────────────►      [END]
```

| Узел | Что делает |
|---|---|
| **Rewrite Query** | LLM превращает вопрос пользователя в поисковый запрос: извлекает ключевые сущности, убирает шум. Выполняется только на 1-м ретрае: первый поиск всегда идёт по исходному вопросу, чтобы не размыть точные идентификаторы (`TOKEN_EXPIRY_HOURS` и т.п.); промпт содержит few-shot пример и требование сохранять идентификаторы as-is |
| **Retrieve** | Вызов `HybridRetriever` по текущему поисковому запросу (`rewritten`; при старте равен вопросу); результат RRF-слияния пишется в состояние графа |
| **Grade Chunks** | Корректирующий шаг. Все чанки оцениваются **одним батч-вызовом** LLM (экономия латентности): модель возвращает JSON `{"results":[{"index":1,"relevant":true},...]}` в режиме `format=json`. Строгий системный промпт: «релевантен ли чанк вопросу — да/нет, без домыслов». Если ответ не распарсился — fallback: считаем все чанки релевантными, чтобы не блокировать генерацию |
| **Conditional Edge** | Генерация — если релевантных чанков ≥ `MIN_RELEVANT` (2 из `TOP_K`=5) **или** циклы исчерпаны. Коррекция — иначе: 1-й ретрай — Rewrite Query, 2-й и далее — Broaden Query → `loop_count += 1` → обратно в Retrieve |
| **Broaden Query** | LLM расширяет запрос (синонимы, общие термины), снимая проблему другой терминологии; выполняется со 2-го ретрая. Few-shot пример в промпте требует сохранять идентификаторы нетронутыми |
| **Generate Answer** | LLM отвечает строго по отфильтрованным чанкам; к ответу прикрепляются уникальные источники (`metadata.source`) |

**Порог грейдинга:** `MIN_RELEVANT_CHUNKS = 2` из `TOP_K = 5` (конфигурируется).
**Предохранитель:** максимум `MAX_RETRIEVAL_LOOPS = 2` коррекций запроса
(rewrite + broaden), после чего принудительная генерация с тем, что найдено
(защита от зацикливания).

## 6. Персистентность и жизненный цикл индекса

- **ChromaDB** персистентна на диске (`CHROMA_DIR`): векторный индекс переживает рестарт.
- **BM25** — in-memory (по ТЗ). При рестарте он **автоматически восстанавливается**
  из ChromaDB (`all_chunks()`), без пересканирования файлов и без повторного вызова
  эмбеддингов — дёшево и всегда консистентно с векторной базой.
- Повторный `index_folder` по тем же файлам идемпотентен: перед записью удаляются
  чанки этих файлов (`delete_by_sources`), затем добавляются свежие.
- Статистика `index_status` после рестарта: счётчик чанков берётся из ChromaDB,
  время последней индексации сбрасывается (`null`) до первого нового запуска.

## 7. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Ollama недоступна | Инструмент возвращает понятное сообщение с подсказкой запуска (`docker compose up -d ollama`), а не traceback |
| Индекс пуст | `ask_question` / `find_relevant_docs` возвращают подсказку вызвать `index_folder` |
| Сетевая ошибка Ollama | Retry (2 попытки) с экспоненциальным backoff, затем ошибка наверх |
| Нераспарсиваемый JSON грейдера | Fallback: все чанки считаются релевантными — генерация не блокируется |
| Неподдерживаемый/нечитаемый файл | Пропускается с предупреждением в результате индексации |

## 8. Стратегия нарезки чанков (Chunking Strategy)

Разбиение адаптировано под природу данных (подробный отчёт — в `README.md`):

| Тип | Файлы | Подход |
|---|---|---|
| Текст/документация | `.md`, `.txt` | `RecursiveCharacterTextSplitter`, 1000 / overlap 150 — контекст не теряется на стыках |
| Исходный код | `.py`, `.js`, `.ts` | `RecursiveCharacterTextSplitter.from_language()` с синтаксисом конкретного языка — резка по границам функций/классов, логические блоки не рвутся |
| Структурированные данные | `.json`, `.yaml` | Парсинг как объекта; текст строится по логическим группам верхнего уровня (путь ключа + значение) с сохранением иерархии, чтобы модель сопоставляла ключи и значения |

`line_number` вычисляется приблизительно: чанки текста/кода идут последовательно,
позиция ищется в исходном файле от курсора предыдущего чанка; для синтезированного
текста JSON/YAML поле равно `null`.

## 9. Отклонения от ТЗ (осознанные)

- **Свой RRF вместо готового `EnsembleRetriever`.** Формула та же, но собственная
  реализация в `HybridRetriever` даёт контроль над токенизацией BM25 (camelCase/snake_case),
  параллельным запуском и детерминизмом слияния; `langchain-text-splitters` из экосистемы
  LangChain используются для чанкинга.
- **Явная передача эмбеддингов в ChromaDB** вместо встроенного `embedding_function` —
  так переключение провайдера (опциональное задание) не требует правок адаптера.

## 10. Тестирование и CI

- **Unit-тесты без сети и без LLM:** fake-реализации `VectorStorage`, `SparseStorage`,
  `LLMService`, `EmbeddingService`; проверяются RRF-слияние, токенизация BM25,
  сплиттеры (включая JSON/YAML и код), метаданные чанков, полный граф
  (happy-path + retry-цикл + исчерпание циклов), адаптер ChromaDB с fake-эмбеддингами.
- **CI (GitHub Actions):** `ruff check` + `pytest` на Python 3.12; сборка Docker-образа —
  отдельной job'ой (опционально по ТЗ).
