# 07. Индексация: замеры, прогресс, персистентность BM25

## Вопрос «сколько занимает индексация?»

Первое затруднение: `index_status` время не возвращает, в логах.duration тоже
не было. Первая попытка замера — прямой вызов index_folder с таймером — была
прервана пользователем. Вторая (после появления прогресса) удалась:

**22 файла, 818 чанков, 0 пропущено, 339.78 c (~5.7 мин) ≈ 0.42 c/чанк**
(CPU, nomic через ollama). Забавный момент прогона: curl с -m 300 оборвал стрим
за секунды до финала — но `index_status` показал обновлённый last_indexed_at,
по нему и поймали завершение; полный второй прогон дошёл до результата.

Загадку «818 vs 1148» решили по ходу: 1148 — это **всего в базе** (330 чанков
демо-файлов из самого первого прогона /data/docs), 818 — чанки proust-корпуса
текущего прогона. Бага нет, книгаучёт.

## Ускорит ли урезание корпуса с 500 до 250 КБ?

Да — **пропорционально ~2x**: стоимость эмбеддингов линейна по чанкам
(~1148 → ~570). Нюанс из кода: переиндексация **всегда полная**
(delete_by_sources + перезапись), инкремента нет — так что 2x на каждом
запуске. BM25-перестройка копеечная. Но «платно»: теряем половину базы знаний.
Тот же 2x даст GPU-проброс — без потери корпуса.

## «Передача чанками улучшила индексацию?»

Нет — скорость не менялась. Батчи по 64 (`_EMBED_BATCH`) **уже были** в коде
(indexer.py:95) — мы не резали один большой запрос, а добавили прогресс поверх
существующих батчей. Польза — видимость, не скорость.

## Прогресс индексации: как договаривались и что сделали

Пользователь хотел видеть прогресс «прям в opencode». Обсудили два механизма:

1. логи сервера (гарантированно);
2. MCP progress-нотификации — но оговорили честно: рендеринг в opencode
   **не документирован**; если клиент не шлёт progressToken, сервер молчит.

Техническая деталь, без которой прогресса бы не было: эмбеддинги уходили бы
одним POST — «между началом и концом» репортить нечего. К счастью, батчи по 64
уже существовали — осталось протянуть колбэк.

Реализация (коммит b8170c6):
- `indexer.py`: `on_progress(done, total, msg)` на каждый батч + logger.info
  «эмбеддинги N/M»; ошибки колбэка не роняют индексацию (_report в try/except);
- `server.py`: tool стал **async** — indexer в `asyncio.to_thread`, из
  рабочего потока прогресс мостом `asyncio.run_coroutine_threadsafe(...) →
  ctx.report_progress(done, total, message)`. Отдельно проверили по исходникам
  fastmcp: без progressToken report_progress — тихий no-op, не ошибка.
- ruff + 25 тестов зелёные; живой прогон подтвердил и логи, и финальный JSON.

## Где живёт индекс

- Docker: volume `chroma_data` → /var/lib/docker/volumes/project_chroma_data
  /_data (CHROMA_DIR=/app/data/chroma); в git не попадает → свежий клон = пустой
  индекс (что и требует чек-лист сдачи: index_status → пусто).
- **BM25 — in-memory**, перестраивается из ChromaDB на старте без эмбеддингов
  (server.py:81-84).

## Персистентность BM25: возможно ли и нужно ли

Возможно: rank_bm25 не умеет save/load, но BM25Okapi пиклится —
`bm25.pkl` + фингерпринт корпуса (число чанков + hash источников), инвалидация
при несовпадении. **Нужно ли: нет** — пересбор из 1148 чанков занимает секунды
(долгий первый старт — это импорт chromadb, не BM25), а «Chroma = единственный
источник истины» исключает целый класс багов рассинхрона. Оправдано при
~100k+ чанков или частых рестартах.
