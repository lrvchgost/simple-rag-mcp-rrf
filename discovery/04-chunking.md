# 04. Чанкинг: почему 1000 и как ещё можно

## Как разговор зашёл

Разбирая пайплайн, пользователь попросил объяснить «принцип разбиения на
чанки и работу поиска по векторам». Отвечали на фактах их же кода.

## Почему режем по ~1000 символов

Это компромисс между двумя провалами:

- **Слишком крупно** (2-4k+): эмбеддинг сжимает карточку в **одну точку** —
  если в карточке несколько тем, смысл усредняется («каша»), точка уже не
  близка ни к чему конкретному; плюс в контекст генерации попадает мусор
  вокруг ответа.
- **Слишком мелко** (<300): мысль рвётся — карточка «он женился на ней» без
  имени не находится ни BM25, ни векторами; чанков втрое больше → дольше
  индексация, больше шума в грейдере.
- **1000 симв. ≈ 200-250 токенов** — «законченный абзац»: карточка
  самодостаточна, топ-5 карточек (~5k симв.) влезает в контекст qwen.

## Как режем у вас (indexer.py:100-109)

- код .py/.js/.ts — сплиттер знает язык, режет по функциям/блокам;
- .md/.txt — RecursiveCharacterTextSplitter: \n\n → \n → слова (резать там,
  где мысль кончилась);
- .json/.yaml — своя логика (indexer.py:125): настройка верхнего уровня —
  чанк целиком, чтобы настройку не разрезало пополам.

**Перекрытие 150 символов** (chunk_overlap): соседние карточки делят «хвост» —
фраза, разрезанная границей, лежит целиком хотя бы на одной карточке. В README
даже есть тест на стыки. Настраивается env: CHUNK_SIZE/CHUNK_OVERLAP
(config.py:37-38) — без правки кода.

## На что влияет размер

точность/полнота поиска; число чанков → время индексации (линейно: 550 КБ →
818 чанков, замер 339.78 c в 07-indexing.md); качество работы грейдера и
генератора (самодостаточность карточек).

## Как ещё можно (обсудили таблицей)

| Способ | Суть | Цена |
|---|---|---|
| по токенам (256-512 tok) | стабильно между языками — кириллица «толще» символов | почти бесплатно |
| структурно: заголовки MD, AST кода | резать там, где логика кончилась | сплиттер на формат (для JSON/YAML вы уже так делаете!) |
| семантический (SemanticChunker) | режет по резкому спаду схожести соседних предложений = смена темы | дорогая индексация |
| small-to-big / parent-child | ищем мелкой точной карточкой, в LLM отдаём родительский раздел | два уровня хранения |
| late chunking | эмбеддим весь документ, режем после | нужна длинноконтекстная эмбед-модель |

Вердикт обсуждения: для корпуса Пруста (главы ~45 КБ, диалоги) текущие
1000/150 — разумный дефолт; первый содержательный апгрейд — parent-child,
а не семантический чанкинг.
