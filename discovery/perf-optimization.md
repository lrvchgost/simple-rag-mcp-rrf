# Perf Optimization — итоги цикла оптимизации RAG (2026-09-27)

Цикл: аудит узких мест → eval-инфраструктура → приоритет №1 (refusal).
Исходное состояние: качество оценивалось «на глаз» (2-3 вопроса), отказов нет,
генератор галлюцинировал на вне-корпусных вопросах.

## 1. Что нашли аудитом

| Стадия | Метрика | До |
|---|---|---|
| Поиск | recall@5 / MRR | 1.0 / 0.625 — здоров |
| Грейдер | gold-preservation | 8/12 (67%) |
| Refusal | честный отказ | 0/2 |
| Генерация | fact_ok | 3/12 (25%) |

Вывод аудита: поиск не узкое место; потери — грейдер (теряет gold в 1/3) и
генерация (тощие/выдуманные ответы). Полный разбор: performance-audit-20260927-2202.md.

## 2. Построена eval-инфраструктура (шаги 1-6)

- `evals/golden.json` v3 — 14 вопросов (5 тех + 7 литературных + 2 refusal),
  разметка expected_chunk (файл:строка + quote), факты на языке ответов;
- `scripts/eval_retrieval.py` — recall@5 + MRR, режимы `--grade`, `--filter`,

- CI: job `eval-retrieval` (tech-подмножество, зелёный на ран #9).

## 3. Приоритет №1 — refusal-логика (выполнен)

| Критерий | До | После |
|---|---|---|
| Refusal (вне-корпусные) | 0/2 | **2/2** |
| Gold-preservation | 8/12 | **9/12** |
| fact_ok | 3/12 | **4/12** |
| Unit-тесты | 25 | 28 |

### Как это делалось (2 итерации + находка)

1. **Промпт escape-hatch** («if NONE related → all false»): отказ не заработал —
   3b игнорирует «NONE related», стал даже щедрее (5/5 шума на kubernetes).
   Побочно gold-preservation выросла до 9/12.
2. **Лексический затвор** в `_generate` (латинские запросы: если удержанные
   чанки не делят с запросом ни одного содержательного токена → отказ):
   частично обходится — rewrite загрязняет запрос корпусными словами
   («swallow» — птица в текстах Пруста).
3. **Фактическая защита — честность генератора:** на пустом по смыслу контексте
   3b сам отвечает «context does not contain any information...» — софт-отказ
   без выдуманных фактов. Eval-детектор дополнен семантическими маркерами
   (does not contain / does not mention).

### Урок

Canned-ветка отказа в Corrective RAG недостижима при «unsure→true»-грейдере
на 3b: ни промпт, ни лексика не заставляют малую модель сказать «все false».
Последнюю линию обороны держит честность генератора. Код оставлен как
defense-in-depth (затвор + escape-hatch + двуязычная заглушка).

## 4. Текущее состояние системы

| Стадия | Вердикт |
|---|---|
| Поиск | здоров (recall 1.0), MRR 0.625 — резерв в ранжировании |
| Грейдер | 9/12 gold-preservation; ЛОСТ-ы плавают между прогонами (дисперсия 3b) |
| Refusal | 2/2 софт-отказ |
| Генерация | 4/12 fact_ok — по-прежнему главное узкое место |

Наблюдение: вопрос-уровневые результаты нестабильны между прогонами
(cottard-meet: preserved → LOST; vinteuil-neighbours: 0.00 → 0.55) —
дисперсия 3b при temperature>0; агрегаты устойчивы.

## 5. Оставшиеся приоритеты

1. **Реранкер (cross-encoder, bge-reranker-v2-m3)** вместо 3b-грейдера:
   MRR 0.625 → ≥0.8, fact_ok 4/12 → ≥6/12. Критерии уже в baseline'ах.
2. **Крупная модель для generate на GPU** (nvidia-container-toolkit +
   docker-compose.gpu.yml): fact_ok → ≥8/12; судить отдельной крупной моделью.
3. Фоновое: parent-child чанкинг, чистка стейл-чанков (после CI-репродукции
   volume пересоздан — стейлов больше нет), осознанная перезапись baseline'ов.
