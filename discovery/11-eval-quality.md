# 11. Оценка качества RAG: golden-набор, recall@k и план внедрения

## Как разговор зашёл

Обсуждали тему №1 из [10-open-topics.md](10-open-topics.md). Стартовый тезис:
весь A/B в сессии (03-grader-generator.md) делался «на глаз» на 2-3 контрольных
вопросах — это не защита от регрессий. Решили разобрать системно и составить
план **без реализации** (решение пользователя).

## Ключевая идея: мерить стадии по отдельности

Пайплайн — retrieve → grade → generate. «Качество RAG» — не одна метрика, а
три, с разными затратами:

| Стадия | Метрика | Нужен LLM? |
|---|---|---|
| retrieve (find_relevant_docs) | recall@k, MRR | нет — детерминированно, в CI |
| grade | precision/recall отметок против золотых меток | нет |
| generate (ask_question) | faithfulness, answer correctness | да (LLM-as-judge) |

Обоснование на собственных кейсах сессии — по живому примеру на каждую стадию:
- retrieve: правильный чанк про Вентёя найден рангом 2 (06-hybrid-search.md);
- grade: до фикса резал золотое (Одетта, 1/5, 03-grader-generator.md);
- generate: наврал при верном контексте («жена принцессы де Лом»).

Мораль: сегодня регрессию чанкинга/RRF/промпта грейдера замечаем только
случайно — метрики по стадиям делают это автоматическим.

## Golden-набор: состав (12-20 вопросов)

Формат записи: `question`, `expected_chunk` (файл + строка или дословная
цитата), `expected_answer` (опционально), `expect_refusal` (флаг).

1. **5-7 технических** — BM25-дружелюбные, точные идентификаторы:
   `TOKEN_EXPIRY_HOURS`, ротация ключей AuthService.
2. **5-7 литературных** — сиды, проверенные в сессии:
   - Коттар → La Raspelière (vol2_01, vol2_04);
   - Вентёй/«nice neighbours» → тётя Селин (vol1_02:137);
   - Одетта → vol2_03 + characters.md.
3. **3-4 каверзных**: переформулировка («Where should we meet Cottard?» vs
   «Where does Cottard spend summer?»); вопрос по стыку чанков (тест overlap
   из README); **expect_refusal** — вопрос не из корпуса («airspeed of an
   unladen swallow») — система должна честно отказаться; это тоже качество.
4. 1-2 вопроса уровня «сёстры»: правильный чанк соседствует с похожим
   отвлекающим (ловит и MRR, и генератор).

## Метрики «на пальцах»

- **recall@5** = доля вопросов, где golden-чанк попал в топ-5. Пороги старта:
  ≥ 0.9 технические, ≥ 0.7 литературные. Реализация тривиальна —
  find_relevant_docs возвращает source + line_number.
- **MRR** = среднее 1/ранг первого правильного чанка. Ловит случай «сёстры»:
  правильный чанк на ранге 2 → вклад 0.5; recall сказал бы «ок», MRR — «деградация».
- **grade precision/recall**: золотые метки релевантности на тех же вопросах →
  сравнение с вердиктами грейдера. Поймает регрессию промпта (верни «strict» —
  CI покраснеет).
- **faithfulness** (generate): judge-LLM получает {контекст, ответ} и проверяет
  выводимость каждого утверждения; поймал бы «жена принцессы де Лом».
- **answer correctness**: сравнение с expected_answer по рубрике.

## Честное ограничение judge

Судить 3b-ответы моделью 3b ненадёжно (субъект и объект совпадают). Варианты:
рубрика с обязательной цитатой из контекста на каждое утверждение; либо более
крупный judge — но на CPU 7b медленный. Компромисс: retrieval-метрики в CI
всегда; generation-eval — вручную/ночью, judge с quote-рубрикой.

## Куда класть в проекте (архитектура плана)

```
evals/
  golden.json              # 12-20 вопросов по формату выше
scripts/
  eval_retrieval.py        # recall@5 + MRR + grade-precision; без chat-LLM
  eval_generation.py       # faithfulness/correctness; judge, ручной/ночной запуск
```
Прогон — через реальный MCP (curl-паттерн из 08-mcp.md) либо прямой импорт
графа; отчёт per-question + агрегат + сравнение с сохранённым baseline.

## План внедрения (без реализации)

1. **golden.json v1** — набить 12-15 вопросов из проверенных в сессии кейсов
   (сид-таблица выше); размечать expected_chunk по line_number из
   find_relevant_docs — половина работы уже сделана живыми прогонами.
2. **eval_retrieval.py** — recall@5 + MRR по find_relevant_docs; вывод
   per-question + агрегат; гонять при каждом изменении чанкинга/RRF/эмбеддера.
3. **Baseline** — зафиксировать текущие цифры (после фикса грейдера) в
   evals/baseline.json; любой следующий эксперимент (реранкер, чанкинг,
   parent-child) сравнивается с ним.
4. **grade-метрики** — отдельным режимом eval_retrieval.py (golden-метки
   релевантности), чтобы ловить регрессии промпта грейдера.
5. **eval_generation.py** — последним: judge с quote-рубрикой; запуск вручную
   перед сдачей/ночью; не в обязательный CI (CPU, медленно).
6. Критерий готовности шага 1-2: `python scripts/eval_retrieval.py` за минуту
   печатает таблицу и падает с ненулевым кодом при recall@5 ниже порога —
   тогда его можно вешать на CI.
