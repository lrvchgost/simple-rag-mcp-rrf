# 01. Segfault ollama: расследование и откат

## Как началось

Пользователь запустил `ollama run qwen2.5:1.5b-instruct` и получил:
`Error: 500 Internal Server Error: llama-server process has terminated: signal: segmentation fault (core dumped)`.

Вопрос был практический: модель вчера работала — что сломалось?

## Расследование по шагам

**Шаг 1 — журналы.** journalctl -u ollama показал ключевое: модель загружалась,
все 29 слоёв уходили на GPU, но не через CUDA, а через **Vulkan**: `offloading
27 repeating layers to GPU`, `Vulkan0 model buffer size = 752.12 MiB`. Дальше —
мгновенный segfault. То есть падает не чтение модели, а запуск инференса.

**Шаг 2 — версия.** `ollama --version` → 0.31.1. Пользователь ранее работал на
другой версии. Железо: Intel UHD 620 (iGPU) + NVIDIA MX150 — Vulkan выбрал
Intel-видео, и именно его драйвер/бэкенд падал.

**Шаг 3 — проверка гипотезы «битая модель».** Перекачали `ollama pull` —
segfault остался. Гипотеза отброшена: дело не в данных.

**Шаг 4 — поиск «выключателя» Vulkan.** Прошлись `strings` по бинарю ollama и
его библиотекам: среди OLLAMA_* переменных нашлась `OLLAMA_VULKAN`. Попробовали
создать systemd override с `Environment="OLLAMA_VULKAN=0"` — но `sudo` запросил
пароль (у агента его нет), команды отдали пользователю.

**Шаг 5 — решение пользователя.** Проще оказалось не воевать с Vulkan:
пользователь вспомнил, что на диске лежит скачанный tgz с ollama 0.5.12
(`/tmp/opencode/ollama-0.5.12.tgz`, 1.5G), который «нормально работает с
текущим драйвером». Проверили содержимое: CUDA-раннеры v11/v12, никакого
Vulkan — падать нечему в принципе.

## Решение

```bash
sudo systemctl stop ollama
sudo tar -C /usr/local -xzf /tmp/opencode/ollama-0.5.12.tgz
sudo systemctl restart ollama
ollama run qwen2.5:1.5b-instruct "hi"   # работает
```

Проверка `ollama ps`: **9%/91% CPU/GPU** — модель грузится через CUDA на MX150,
9% слоёв не влезли в 2 ГБ VRAM. Важный побочный вывод: сегфолт был специфичен
для 0.31.1 + Vulkan; на 0.5.12 этого кода просто нет.

## Обсуждение «а поможет ли откат?»

Перед откатом пользователь спросил «это пофиксит ошибку?» — аргументировали
заранее: раз в 0.5.12 нет Vulkan-раннера, соответствующий путь исполнения
отсутствует; формат GGUF моделей совместим; CUDA-раннеры на месте. Прогноз
сбылся — полезная проверка привычки «объяснить, почему фикс сработает, до
фикса».

## Дальше по цепочке: GPU в Docker

Обсудили, что хостовый ollama (0.5.12) и докерный — независимые миры: RAG-стек
живёт в контейнере с `CUDA_VISIBLE_DEVICES=-1` (docker-compose.yml), так что
«91% GPU» на хосте ничего не даёт RAG'у.

Первый вариант правки — `gpus: all` прямо в docker-compose.yml — был
отвергнут после вопроса «другой человек сможет запустить это у себя?»: без
NVIDIA/toolkit у преподавателя упал бы сам `docker compose up`. Переписали на
опциональный override `docker-compose.gpu.yml`:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d
```

Базовый CPU-вариант работает на любом железе; README задокументирован
(коммит `59920b2`). Для MX150 2 ГБ честно оговорили: 3b целиком не влезет —
частичная выгрузка слоёв, ускорение ~x2-4, а не x10; nomic (~275 МБ) уйдёт
целиком.

## Урок

`ollama/ollama:latest` — лотерея: между 0.5.12 и 0.31.1 появился Vulkan-путь,
который на нашем железе сегфолтит. Пиннить версии образов — тема №3 в
[10-open-topics.md](10-open-topics.md).
